# KCG Health OSM — Product Definition v0.2

สถานะ: Product direction agreed with project owner
วันที่: 2026-08-27

## 1. Product Core
KCG Health OSM คือระบบสำหรับ **ออกแบบ กระจาย กรอก ตรวจ และติดตามแบบคัดกรองสุขภาพระดับชุมชน** โดยเชื่อมการทำงานระหว่าง:

`แพทย์/เจ้าหน้าที่ รพ.สต. → อสม. → ครัวเรือน/ประชาชน → กลับสู่แพทย์/เจ้าหน้าที่`

ระบบนี้ไม่ใช่ Smart อสม. และไม่พยายามแทนระบบของรัฐ แต่ต้องช่วยจัดข้อมูลให้เป็นระเบียบ ตรวจง่าย ติดตามได้ และเตรียมให้อยู่ในรูปแบบที่สามารถนำไปใช้ต่อกับ Smart อสม. หรือระบบทางการได้ในอนาคตเมื่อทราบช่องทางที่ถูกต้อง

## 2. ผู้ใช้เวอร์ชันแรก
มี 3 กลุ่มหลักตั้งแต่ต้น:
1. แพทย์/เจ้าหน้าที่ รพ.สต.
2. อสม.
3. ประชาชน

ประชาชนมีบัญชี/ตัวตนในระบบตั้งแต่เวอร์ชันแรก แต่ความสามารถฝั่งประชาชนจะเปิดเท่าที่จำเป็นก่อน

## 3. ใครเริ่มงาน
ในเวอร์ชันแรก **แพทย์/เจ้าหน้าที่เป็นผู้เริ่มงาน**

งานเริ่มจากการสร้างแบบคัดกรองหรือภารกิจคัดกรอง แล้วกำหนดกลุ่มเป้าหมายและส่งออกไปยังประชาชน/อสม.

อสม.และประชาชนยังไม่ใช่ผู้สร้าง campaign หลักด้วยตนเองใน MVP

## 4. Form Builder — หัวใจของระบบ
แพทย์/เจ้าหน้าที่ต้องสามารถสร้างแบบฟอร์มเองได้อย่างยืดหยุ่น ไม่จำกัดเฉพาะ NCD

ตัวอย่างชนิดคำถาม:
- short text
- long text
- number
- checkbox
- radio
- dropdown/select
- date
- time
- yes/no
- single choice / multiple choice
- required / optional

ความสามารถขั้นต่ำของ Form Builder:
- เพิ่ม/ลบ/เรียงคำถาม
- ตั้งชื่อแบบฟอร์มและคำอธิบาย
- กำหนดตัวเลือกของคำถาม
- กำหนด required/optional
- preview ก่อนส่ง
- version form หลังเผยแพร่ เพื่อไม่ทำลายคำตอบเก่า

## 5. การเลือกกลุ่มเป้าหมาย
แพทย์/เจ้าหน้าที่ต้องเลือกผู้รับแบบฟอร์มได้หลายระดับ:
- รายบุคคล
- รายครัวเรือน
- รายหมู่บ้าน/พื้นที่
- ตามเงื่อนไข เช่น อายุ กลุ่มเสี่ยง หรือคุณสมบัติที่มีใน master data

ระบบต้อง resolve กลุ่มเป้าหมายออกมาเป็นรายการบุคคลจริงก่อนส่ง เพื่อให้ติดตามสถานะรายคนได้

## 6. โครงสร้างพื้นที่และความรับผิดชอบ
โครงสร้างหลัก:

`ตำบล → หน่วยบริการ → หมู่บ้าน → อสม. → ครัวเรือน → สมาชิกในครัวเรือน`

ตัวอย่าง:
- หมู่บ้านหนึ่งมี อสม. หลายคน
- อสม.แต่ละคนรับผิดชอบหลายครัวเรือน
- แต่ละครัวเรือนมีสมาชิกหลายคน
- ประชาชนแต่ละคนต้องทราบว่าอยู่ครัวเรือนใดและอยู่ในความรับผิดชอบของ อสม.คนใด

การกำหนดว่า อสม.คนใดดูแลครัวเรือนใด ทำได้โดย:
- แพทย์/เจ้าหน้าที่
- ประธาน อสม./ผู้ประสานงาน

## 7. การนำเข้าข้อมูลประชาชนครั้งแรก
ใช้แนวทางผสม:
1. เจ้าหน้าที่/แอดมิน import หรือกรอกข้อมูลตั้งต้น
2. อสม.ช่วยตรวจ แก้ และเพิ่มครัวเรือน/สมาชิกที่ตกหล่นในพื้นที่รับผิดชอบ

การแก้ข้อมูล master ต้องมี trace และสิทธิ์ ไม่ควรแก้ข้อมูลอ่อนไหวแบบไม่มีประวัติ

## 8. สองเส้นทางการกรอกแบบฟอร์ม
### กลุ่ม A — ประชาชนใช้มือถือได้
ประชาชนเข้าแอปหรือเข้าผ่านวิธีที่ได้รับอนุญาต แล้วกรอกแบบฟอร์มเอง

แม้กรอกเอง ระบบยังต้องผูกประชาชนกับ อสม.ที่ดูแลครัวเรือนนั้น

### กลุ่ม B — ประชาชนใช้มือถือไม่ได้/ไม่ถนัด
อสม.ที่รับผิดชอบเป็นผู้กรอกแทนประชาชน

ทุกคำตอบต้องเก็บ provenance ว่า:
- ใครคือเจ้าของข้อมูล/ผู้ถูกคัดกรอง
- ใครเป็นผู้กรอกจริง
- กรอกเองหรือกรอกแทน
- เวลา/แบบฟอร์มเวอร์ชันใด

## 9. วิธีเข้าใช้งานของประชาชน
รองรับหลายรูปแบบในสถาปัตยกรรม:
- OTP เบอร์โทร
- บัญชีใช้งานต่อเนื่อง
- ลิงก์เฉพาะบุคคล/QR สำหรับภารกิจเฉพาะ
- อสม.กรอกแทนโดยไม่ต้องให้ประชาชนล็อกอินเอง

MVP ไม่จำเป็นต้องเปิดทุกวิธีพร้อมกัน แต่ architecture ต้องไม่ปิดทางเลือกเหล่านี้

## 10. หลังส่งแบบฟอร์ม
แพทย์กำหนดตอนสร้าง/เผยแพร่แบบฟอร์มได้ว่า:
- ต้องตรวจทุกคำตอบ
หรือ
- ให้ระบบรับคำตอบทั่วไป และส่งเฉพาะรายการผิดปกติ/เข้ากติกาที่กำหนดมาให้ตรวจ

ระบบต้องแยกชัดเจนระหว่าง:
- submitted
- requires review
- reviewed
- action required
- completed

## 11. Dashboard ฝั่งแพทย์/เจ้าหน้าที่
Dashboard ต้องตอบได้ว่า:
- ส่งแบบฟอร์มไปกี่คน
- กรอกแล้วกี่คน
- ยังไม่กรอกกี่คน
- มีผลที่ต้องตรวจกี่คน
- งานค้างอยู่ที่ใคร
- ความคืบหน้าแยกตาม หมู่บ้าน → อสม. → ครัวเรือน → ประชาชน

ต้อง drill down ได้จากภาพรวมจนถึงรายบุคคลตามสิทธิ์

## 12. การติดตามหลังพบความผิดปกติ
ระบบต้องรองรับ action ต่อเนื่องโดยแพทย์/เจ้าหน้าที่ เช่น:
- มอบหมายให้อสม.ติดตาม/วัดซ้ำ
- นัดประชาชนมาที่ รพ.สต.
- ส่งต่อหน่วยบริการอื่น
- บันทึกว่าได้รับการตรวจ/จัดการแล้ว

รายละเอียด workflow เชิงคลินิกและเกณฑ์คัดกรองต้องได้รับการยืนยันจากบุคลากรสุขภาพก่อน production

## 13. Smart อสม. Boundary
ใน MVP:
- **ยังไม่สร้าง integration อัตโนมัติ**
- ระบบต้องสามารถจัดข้อมูลคำตอบให้อยู่ในรูปแบบที่ export/ถ่ายโอนไปใช้ต่อได้
- รูปแบบ export ที่แท้จริงต้องศึกษาจากช่องทางที่ Smart อสม. รองรับอย่างถูกต้องก่อน

ห้าม scrape, auto-fill หรือเชื่อมระบบรัฐแบบไม่รับอนุญาต

## 14. สิ่งที่ไม่ใช่แกนหลักของ MVP
- ไม่ใช่ระบบเยี่ยมบ้านทั่วไป
- ไม่ใช่ full EMR/HIS
- ไม่ใช่ระบบวินิจฉัยโรค
- ไม่ใช่ระบบค่าป่วยการ
- ไม่ใช่ระบบประชาชนเปิดเคสเองเป็น workflow หลัก
- ไม่ล็อกระบบไว้กับฟอร์ม NCD เพียงแบบเดียว

## 15. Product Workflow ใหม่
แกนหลัก:

`Create Form → Define Audience → Publish → Route to Citizen/Volunteer → Complete Form → Submit → Review Rules → Staff Review → Follow-up/Referral/Complete → Export-ready`

## 16. MVP ที่ควรพิสูจน์ก่อน
1. แพทย์สร้างแบบฟอร์มเองได้
2. เลือกผู้รับแบบหลายระดับได้
3. ประชาชนตัวอย่างกรอกเองได้
4. อสม.กรอกแทนประชาชนในครัวเรือนรับผิดชอบได้
5. ระบบผูกทุกคำตอบกับบุคคล ครัวเรือน อสม. และแบบฟอร์มเวอร์ชันได้
6. แพทย์เห็น dashboard ความคืบหน้าและรายการที่ต้องตรวจได้
7. แพทย์สร้างการติดตามต่อจากคำตอบได้
8. ข้อมูล export ออกมาเป็นโครงสร้างที่พร้อม mapping ไปยังระบบภายนอกภายหลัง

## 17. การตัดสินใจที่ให้ทีมออกแบบต่อได้เอง
- รูปแบบ UI ของ Form Builder
- exact component library
- visual design tokens
- schema ภายในของ form definition
- วิธีเก็บ conditional rules
- route naming
- state management
- repository interface pattern
- test framework

แต่ต้องไม่เปลี่ยน Product Workflow และบทบาทหลักโดยไม่อัปเดตเอกสารนี้ก่อน
