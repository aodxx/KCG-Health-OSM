# D1 — Field Workflow & Data Mapping

สถานะ: Working discovery document
วันที่: 2026-08-26

## 1. เป้าหมาย

ระบุพื้นที่รับผิดชอบจริง โครงสร้างการทำงานของ อสม./รพ.สต. และระบบข้อมูลเดิม เพื่อใช้เป็นฐานก่อนสร้าง System Blueprint v0.1 และ PRD

## 2. การแบ่งเขตรับผิดชอบของหน่วยบริการ

จากหลักฐานโครงการสุขภาพพื้นที่ สามารถยืนยันการแบ่งเขตรับผิดชอบเบื้องต้นได้ดังนี้

### รพ.สต.บ้านทุ่งยาว
- หมู่ 1 บ้านควนใหม่
- หมู่ 7 บ้านทุ่งยาว
- หมู่ 9 บ้านไสใหญ่

หลักฐานสำคัญ: โครงการพัฒนาทักษะผู้ดูแลผู้พิการ/ผู้สูงอายุติดบ้านติดเตียงของ รพ.สต.บ้านทุ่งยาว ระบุชุมชนหมู่ 1, 7, 9 โดยตรง และโครงการ CPR ปี 2569 ของ รพ.สต.บ้านทุ่งยาวระบุพื้นที่เสี่ยงหมู่ 1, 7, 9 เช่นกัน

### รพ.สต.บ้านโคกชะงาย
- หมู่ 2 บ้านโคกชะงาย
- หมู่ 3 บ้านโคกกอ
- หมู่ 4 บ้านลำพายตก
- หมู่ 5 บ้านหนองจิก
- หมู่ 6 บ้านโคกมะม่วง
- หมู่ 8 บ้านควน

หลักฐานสำคัญ: โครงการคัดกรองมะเร็งปากมดลูกของ รพ.สต.บ้านโคกชะงายระบุชัดว่าเขตรับผิดชอบคือหมู่ 2,3,4,5,6,8

> สถานะ: ยืนยันได้ในระดับ working baseline จากหลักฐานพื้นที่หลายรายการ แต่ควรตรวจซ้ำกับบัญชีเขตรับผิดชอบล่าสุดของหน่วยบริการก่อน production

## 3. ภาพประชากรและกลุ่มเป้าหมายที่พบ

ข้อมูลเก่าในโครงการของ รพ.สต.บ้านทุ่งยาวระบุว่า หมู่ 1,7,9 เคยมีประชากรรวม 2,692 คน ผู้สูงอายุ 422 คน ผู้สูงอายุติดบ้าน/ติดเตียง 33 คน ผู้พิการ 49 คน และอาสาสมัครผู้ดูแลเฉพาะกลุ่ม 14 คน ข้อมูลนี้มีอายุหลายปีจึงใช้เพื่อออกแบบ capacity เท่านั้น ห้ามใช้เป็นยอดปัจจุบัน

ฝั่ง รพ.สต.บ้านโคกชะงาย มีหลักฐานปี 2565 ระบุผู้สูงอายุในเขตรับผิดชอบ 653 คน และโครงการคัดกรองมะเร็งปากมดลูกเคยระบุกลุ่มเป้าหมายหญิง 30–60 ปี 515 คน

ข้อสรุปเชิงออกแบบ: ระบบต้องรองรับการแบ่งกลุ่มประชากรตาม lifecycle และ risk cohort ไม่ใช่เพียงรายชื่อประชาชนทั้งหมด

## 4. Workflow จริงที่พบ

### 4.1 งานคัดกรอง NCD / สุขภาพเชิงรุก
1. กำหนดกลุ่มเป้าหมาย
2. อสม./เจ้าหน้าที่สำรวจและเชิญเข้าคัดกรอง
3. บันทึกค่าคัดกรอง เช่น ความดัน/น้ำตาล/ปัจจัยเสี่ยง
4. จำแนกผลเป็นปกติ / เสี่ยง / ผิดปกติ
5. ให้คำแนะนำและปรับพฤติกรรม
6. นัดตรวจซ้ำหรือส่งต่อหน่วยบริการ
7. ติดตามผลต่อเนื่อง
8. สรุปผลเป็นตัวชี้วัด/รายงาน

### 4.2 งานเยี่ยมบ้าน / LTC
1. ระบุบุคคลติดบ้าน ติดเตียง ผู้พิการ หรือมีภาวะพึ่งพิง
2. ผูกผู้ดูแล/ญาติ/อสม./หน่วยบริการกับ case
3. วางแผนเยี่ยม
4. บันทึกสภาพร่างกาย จิตใจ ปัญหาการใช้ชีวิต และภาวะแทรกซ้อน
5. ให้คำแนะนำผู้ดูแล
6. แจ้งเจ้าหน้าที่เมื่อพบ red flag
7. นัดติดตาม
8. บันทึกผลซ้ำเป็น longitudinal timeline

### 4.3 งานโรคติดต่อ/ไข้เลือดออก
1. ระบุพื้นที่/ครัวเรือนเป้าหมาย
2. อสม.ลงสำรวจแหล่งเพาะพันธุ์
3. บันทึกผลระดับบ้าน/พื้นที่
4. ทำกิจกรรมแก้ไข/รณรงค์
5. ติดตามซ้ำ
6. สรุปความครอบคลุมและพื้นที่เสี่ยง

### 4.4 งานคัดกรองเฉพาะโรค
หลักฐานมะเร็งปากมดลูกในพื้นที่แสดง workflow: ค้นหากลุ่มเป้าหมาย → ให้ความรู้ → ตรวจคัดกรอง → แจ้งผล → ส่งต่อเมื่อผิดปกติ → ติดตาม

ข้อสรุป: ระบบควรใช้ workflow engine แบบเดียวกันคือ `Target → Task → Observation → Risk → Action → Referral → Follow-up → Closure` แล้วให้แต่ละโครงการ/ภารกิจใช้แบบฟอร์มต่างกัน

## 5. งานที่ Smart อสม. ทำอยู่แล้ว

ข้อมูลกระทรวงสาธารณสุขยืนยันว่า Smart อสม. ใช้เป็นเครื่องมือปฏิบัติงานและรายงานผล อสม. และสัมพันธ์กับรายงาน อสม.1 รวมถึงกิจกรรมสุขภาพเชิงรุก ตัวชี้วัดปัจจุบันยังใช้ข้อมูลการใช้ Smart อสม. ประกอบการประเมินศักยภาพ อสม.

รายงาน อสม. รายเดือนครอบคลุม 9 ภารกิจหลัก ได้แก่
1. ส่งเสริมสุขภาพ
2. เฝ้าระวัง ป้องกัน และควบคุมโรค
3. ฟื้นฟูสุขภาพ
4. คุ้มครองผู้บริโภค
5. จัดการสุขภาพชุมชน/แผนสุขภาพตำบล
6. สนับสนุนอาสาสมัครประจำครอบครัว
7. ใช้ยาอย่างสมเหตุผล/ผลิตภัณฑ์สุขภาพ
8. ร่วมทีมหมอครอบครัวดูแลผู้ป่วย/ครอบครัว
9. กิจกรรมอื่นตามปัญหาชุมชน

### สิ่งที่แอปใหม่ไม่ควรทำซ้ำโดยตรง
- ไม่สร้างระบบจ่ายค่าป่วยการ อสม.
- ไม่สร้างรายงาน อสม.1 เพื่อแทนระบบทางการโดยไม่มี integration ที่ได้รับอนุญาต
- ไม่พยายามแทน HDC หรือฐานข้อมูลเวชระเบียนของสถานบริการ

### ช่องว่างที่แอปใหม่ควรเน้น
- งานประสานรายบุคคลระหว่าง อสม. ↔ ครัวเรือน ↔ เจ้าหน้าที่
- task assignment และ follow-up
- case timeline
- แจ้งเตือน red flag
- dashboard ระดับหมู่บ้าน/เขตรับผิดชอบ
- offline-first field work
- ลดการใช้ LINE/โทรศัพท์/กระดาษในการตามงาน
- export ข้อมูลสรุปเพื่อช่วยกรอกระบบทางการ แทนการสร้างระบบคู่ขนาน

## 6. HDC และข้อมูลสถานบริการ

ตัวชี้วัดกระทรวงจำนวนมากใช้ HDC/โปรแกรมสถานบริการเป็นแหล่งข้อมูล เช่น CVD Risk ในผู้ป่วยเบาหวานและความดัน ดังนั้น KCG-Health-OSM ต้องถือว่า HDC/ระบบสถานบริการเป็น downstream official reporting system ไม่ใช่ฐานข้อมูลที่ควรเลียนแบบ

แนวทางที่ควรออกแบบ:
- แอปเก็บเฉพาะข้อมูลที่จำเป็นต่อ field workflow
- มีสถานะว่า observation ใด `draft / verified / referred / exported`
- หากอนาคตมี API/integration ที่ถูกต้อง ค่อยเพิ่ม adapter
- ห้าม scrape หรืออัตโนมัติกรอกระบบรัฐโดยไม่ได้รับอนุญาต

## 7. Data domains ที่เริ่มชัดเจน

1. ServiceUnit — หน่วยบริการ
2. Village — หมู่บ้าน
3. Household — ครัวเรือน
4. Person — บุคคล
5. Volunteer — อสม.
6. Assignment — ความรับผิดชอบ อสม.ต่อครัวเรือน/บุคคล
7. Case — เคสสุขภาพ/การติดตาม
8. Task — งานที่ได้รับมอบหมาย
9. Visit — การลงพื้นที่/เยี่ยมบ้าน
10. Observation — ค่าคัดกรอง/ผลสังเกต
11. RiskAssessment — การประเมินความเสี่ยง
12. Referral — การส่งต่อ
13. FollowUp — นัด/ติดตามผล
14. Campaign — โครงการ/กิจกรรมสุขภาพ
15. Consent — ความยินยอม/ฐานการประมวลผลข้อมูล
16. Attachment — ภาพ/เอกสารประกอบ โดยต้องมี access control
17. AuditEvent — ประวัติการเข้าถึง/เปลี่ยนแปลงข้อมูล

## 8. Working role model

- Resident / Household Member
- Caregiver
- อสม.
- ประธาน/ผู้ประสาน อสม.
- เจ้าหน้าที่ รพ.สต.
- แพทย์/วิชาชีพที่ได้รับสิทธิ์
- System Administrator

บทบาทไม่เท่ากับสิทธิ์: access ต้องพิจารณา service unit + village + assignment + case relationship ด้วย

## 9. สิ่งที่ยังต้องยืนยันจากพื้นที่จริง

- จำนวน อสม. ปัจจุบันของแต่ละหมู่บ้าน
- อสม. 1 คนดูแลครัวเรือนใดบ้าง
- รายชื่อ/จำนวนเจ้าหน้าที่ของ 2 รพ.สต. ที่จะใช้ระบบจริง
- วิธีที่ อสม.รับงานในปัจจุบัน: ประชุม, LINE, โทรศัพท์, กระดาษ, Smart อสม. หรือหลายช่องทาง
- แบบฟอร์มที่ใช้จริงล่าสุดของแต่ละภารกิจ
- ขั้นตอนส่งต่อจาก อสม.ไป รพ.สต. และจาก รพ.สต.ไปโรงพยาบาล
- ข้อมูลใดที่เจ้าหน้าที่ต้องการเห็นแบบ real-time
- บุคคลในครัวเรือนจะใช้ระบบเองทุกคนหรือให้หัวหน้าครัวเรือน/ผู้ดูแลเป็นผู้แทน
